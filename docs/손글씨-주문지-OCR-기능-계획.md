# 손글씨 주문지 OCR 기능 — 구현 계획

> 약국에서 손으로 작성한 주문지를 사진으로 찍어 업로드하면, OCR(멀티모달 LLM)로
> **약품명 · 포장단위 · 주문수량**을 구조화 추출하여 **날짜 + 주문차수** 단위로 저장하는 기능.
> 홈 화면([templates/home.html](../templates/home.html))의 "준비 중" 카드 자리에 새 진입점으로 추가한다.

---

## 1. 목적 & 사용자 워크플로우

약국은 주로 종이에 약품명/포장단위/주문수량을 수기로 작성한다. 이를 디지털화한다.

```
① 약사가 종이 주문지를 사진 촬영
② (현재 단계) PC에서 이미지 파일 업로드   → (추후) 폰에서 업로드
③ OCR이 약품명 · 포장단위 · 주문수량 3필드로 구조화 추출
④ [검수 화면] 사용자가 추출 결과를 확인·수정 (Human-in-the-loop)
⑤ 날짜 + 주문차수(1~3차)를 선택해 저장
```

- 같은 날짜라도 **주문차수(1~3차)가 다르면 별개 주문**으로 취급한다. 키는 `(날짜, 차수)`.
- 수기 작성이라 OCR 오타가 발생할 수 있어, 약품 마스터 DB를 참조해 **오타 보정 + 후보 제시**를 한다(2단계).

## 2. 확정된 결정사항

| 항목 | 결정 | 비고 |
|------|------|------|
| OCR 엔진 | **멀티모달 LLM (Gemini)** | 웹 Gemini에서 손글씨 인식 검증 완료. 텍스트 추출 + 표 구조 파싱 + 오타보정을 한 번에 처리. `responseSchema`로 3필드 JSON 강제 |
| 검수 방식 | **Human-in-the-loop 필수** | OCR 결과를 바로 저장하지 않고 검수 화면에서 확인·수정 후 커밋. 수량 오독(10↔100)은 금전 사고로 직결 |
| 포장단위 기준 | **기준 도매상 1곳 기준** | 그 도매상에 등록된 단위만 취급 → 1:N 복잡도 제거 |
| 백엔드 DB | **Supabase** | Postgres(관계형) + Storage(이미지) + Auth + Edge Function. 기존 JSON 파일 저장의 한계 해소 |
| 인증 | **이메일 매직링크** | 비기술 사용자(약사)에게 가장 무난. Google OAuth는 localhost 리다이렉트 설정 부담 |
| 데이터 격리 | **RLS (Row Level Security)** | 모든 행/이미지에 `user_id` 태깅, 정책으로 타 약국 데이터 물리적 차단 |
| Gemini 키 보관 | **배포 시 Edge Function** | 배포 바이너리에 키를 심으면 추출·도용됨. Edge Function(서버)에만 키 보관. **단, 로컬 검증 단계에선 불필요**(아래 4단계 참고) |
| 비용 모델 | **중앙 키 + 정액 구독(잠정)** | 호출당 비용이 작아 사용량 정산보다 정액이 단순. 미터링은 가시성+남용캡 목적으로 유지. 실측 후 확정 |

### 보류 / 추후 결정

- **폰 업로드 페이지** — 미니 호스팅 페이지 방향(Supabase Hosting/Vercel에 "촬영→업로드"만 하는 정적 페이지). **마지막 단계로 보류.**
- **약품 마스터 / 기준도매상 단위 채우는 방법** — 엑셀 업로드 vs 기존 스크래퍼 크롤링. (2단계에서 결정)
- **비용 모델 확정** — 실제 주문지 샘플로 호출당 토큰/비용 실측 후 정액 단가 결정.
- **내부 도구 vs 판매 제품** — 비용 모델·배포 구조에 영향. 미확정.

## 3. 아키텍처

### 현재 (기존 앱)
- **Backend**: FastAPI ([web_server.py](../web_server.py)), Python, localhost:8000, PyInstaller 패키징
- **Frontend**: Jinja2 + Vanilla JS ([templates/](../templates/), [static/](../static/))
- **저장**: JSON 파일 (DB 없음)
- **스크래퍼**: Playwright 8개 도매상 ([scrapers/](../scrapers/))

### 목표 (하이브리드)
기존 로컬 전용 기능(품절검색 등)은 그대로 두고, **이 OCR 기능만 Supabase 클라우드 백엔드를 갖는** 하이브리드로 진화.

```
┌─────────────┐   (추후) 사진 업로드   ┌──────────────────────────┐
│  폰 (미니    │ ────────────────────▶ │  Supabase                │
│  업로드 웹)  │                       │   • Auth (매직링크)       │
└─────────────┘                       │   • Storage (이미지, RLS) │
                                      │   • Postgres (RLS)        │
┌─────────────┐   OCR 요청            │   • Edge Function ────────┼──▶ Gemini
│  PC 앱       │ ────────────────────▶ │       (Gemini 키 보관)    │
│ (PyInstaller │ ◀──────────────────── │                          │
│  + 검수 UI)  │   구조화 결과          └──────────────────────────┘
└─────────────┘
```

> **핵심**: "중앙 키냐 약국별 키냐"는 *누가 비용을 내냐*의 문제이고, Edge Function 구조 자체는 어느 쪽이든 동일하게 유지된다(약국별이면 약국 키를 Supabase에 암호화 저장 후 요청자 키로 호출).

## 4. 단계별 구현 계획

### 1단계 — OCR 코어 로컬 검증 ⭐ (현재 목표)
**검증할 핵심 리스크**: "Gemini가 실제 주문지에서 3필드를 안정적으로 추출하는가."
최소 인프라로 빠르게 확인한다. **이 단계에선 Supabase·Edge Function·인증 불필요.**

- 홈 화면 "준비 중" 카드 → 새 페이지/라우트 추가
- PC 파일 업로드 UI (이미 PC에 있는 이미지 가정)
- FastAPI 백엔드가 **.env의 Gemini 키로 직접 호출** (개발 PC라 안전)
- `responseSchema`로 `[{약품명, 포장단위, 수량}]` JSON 강제
- 검수 테이블 화면: 행마다 수정 가능
- (선택) 날짜 + 차수 선택 UI — 저장은 다음 단계

> **열린 결정**: "잘 구동되는지 확인"의 종료 지점을 ⓐ추출→검수 화면까지로 볼지, ⓑ Supabase 저장까지 포함할지. 권장은 ⓐ(핵심 리스크만 빠르게 검증) 후 2단계에서 저장 결합.

### 2단계 — Supabase 영속 저장 + 오타 보정
- Supabase 프로젝트 생성, Postgres 스키마 + RLS, Storage 버킷
- 매직링크 로그인 연동 (로컬 웹 UI에서 Supabase Auth JS)
- `(날짜, 차수)` 키로 주문 + 라인아이템 저장, 업로드 이미지 Storage 보관
- **약품 마스터 + 기준도매상 단위 DB** 구축 (엑셀 업로드 or 크롤링 — 결정 필요)
- 검수 화면에서 자모 분해 기반 fuzzy matching → 후보 드롭다운 제시 (자동 무음 보정 금지)

### 3단계 — 배포 시 키 보안 (Edge Function)
- Gemini 호출을 Python 백엔드 → **Edge Function**으로 이전 (키를 secret으로 서버 보관)
- 사용량 미터링(`user_id` + 토큰) 로깅, 남용 방지 쿼터(월/분당 호출 캡)

### 4단계 — 폰 업로드 편의성
- 미니 업로드 정적 페이지 호스팅, 동일 계정 로그인 → 업로드
- PC 앱은 같은 `user_id`이므로 Storage에서 자동 노출

## 5. 데이터 모델 초안 (Supabase / 2단계)

```
pharmacy_user        : Supabase Auth 계정 (= 약국)         ← RLS 기준 user_id

drug_master          : 약품 마스터
  - id, user_id, 약품명(정식), 보험코드?, 규격?, ...

drug_package_unit    : 기준도매상 기준 포장단위 (마스터당 N개일 수 있으나 기준 1곳만 취급)
  - id, drug_master_id, 단위문자열(정규화)

order                : 주문 (날짜 + 차수 = 유니크)
  - id, user_id, 주문일자, 차수(1~3), image_path(Storage), 생성시각
  - UNIQUE(user_id, 주문일자, 차수)   ← 중복 업로드 시 정책 필요(append/replace/merge)

order_line_item      : 주문 라인아이템
  - id, order_id, 약품명(보정후), 포장단위, 수량, drug_master_id(매칭시), 원본OCR텍스트
```

- **모든 테이블 RLS**: `user_id = auth.uid()` 행만 접근.
- **중복 업로드 정책** 미정: 같은 `(날짜, 차수)`에 재업로드 시 append / replace / merge 중 결정 필요.

## 6. 기술 리스크 & 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| "한 장 성공"이 평균 정확도를 보장 못 함 | OCR 신뢰성 | 실제 주문지 10~20장으로 정확도 실측. **검수 화면 필수** |
| 수량 오독(10↔100) | 금전 사고 | Human-in-the-loop 검수에서 사용자 확정 |
| 한글 자모 기반 fuzzy matching 난이도 | 오타보정 품질 | 초/중/종성 분해 기반 유사도, 임계값 튜닝, 후보 제시(자동 무음 보정 금지) |
| 배포 바이너리의 키 유출 | 비용 도용 | Gemini 키는 Edge Function에만. Supabase **anon key**는 공개 안전(RLS가 방어) |
| 기준도매상 단위 staleness | 보정 오류 | 단위 마스터 주기적 갱신 방안 필요(2단계) |
| 모델 티어/비용/지연 | 운영비 | Flash로 시작, 어려운 케이스만 Pro 폴백. 샘플로 실측 |
| 개인정보 외부 전송 | 데이터 거버넌스 | 주문 데이터가 Google/Supabase로 전송됨 — 의식적 수용 |
